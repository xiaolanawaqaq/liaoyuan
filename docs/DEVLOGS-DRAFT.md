## 日志 1：为什么是「可读的涌现」——立项（10/01）

主题「涌现」最容易想到的是堆大量单位跑出意料之外的场面。我选了一个更克制的方向：**少量确定性规则 + 玩家能看见因果**。

《燎原》每格植被只记录类型和热量：邻居燃烧 +1，顺风 +2，达到阈值起火，烧完熄灭。没有随机数参与火势判定。复杂局面（火线分叉、风口突破、隔离带被绕开）全部由这些简单规则「涌现」出来——但玩家每一步都能从橙框预判里看到下一轮将发生什么。

第一版原型当天完成：5 关战役、三种工具（铁锹/斧头/水壶）、一星到三星评价。当天模拟层断言测试约 4 万条。

## 日志 2：把「等待余火」做真（10/03）

早期版本写过一个「自动快进」：当没有燃烧格时自动结束。但代码审计发现这个分支**在正常玩法里根本到不了**——模拟层在火烧尽时已经先判胜负了。一个「已验证的优化」其实从未生效。

v0.3 重做为「等待余火」：每回合结束先在克隆状态上完整模拟最多 40 回合，确认所有房屋都能撑到火烧尽，才显示快进按钮；做不到就不显示。这次不是「看起来能用」，而是模拟结果可证明。配套 GUI 测试覆盖了按钮出现/不出现两种情况。

教训：实现不等于生效，自动化测试要验证触发条件本身可达。

## 日志 3：手机不是缩小屏（10/04）

第一版手机布局是把桌面 UI 直接缩进小窗，结果按钮出屏、模态框关不掉、触屏点格子直接消耗行动点——想看一下格子信息都得花一回合。

改动：

- 加「查看/施工」切换：查看模式点格子只显示信息，不消耗行动点；
- 模态说明改可滚动容器，按视口高度自适应；
- 输入层支持真实 `InputEventScreenTouch/Drag`，并过滤引擎的鼠标模拟事件防止双击；
- 用 `content_scale_size` 做紧凑布局基准，而不是逐控件猜缩放。

回归用了真实输入事件注入的 GUI 测试（290 断言），覆盖三种窗口尺寸截屏检查按钮出界。

## 日志 4：种子挑战与可分享战绩（10/05）

单机解谜的重玩动力来自「同题不同解」和「不同题同公平」。挑战模式输入一个巡护编号（种子），从种子确定性生成河桥地形关卡——河面只留若干缺口可蔓延，天然制造「涌现」式火线瓶颈。

同编号可复现、可分享：结算一键复制战绩文本（关卡、星级、植被保留率、巡护得分），不含任何联网行为，符合赛事离线要求。挑战累计巡护得分与战役星级分开存档；300 个种子的合法通关路径（witness）全部回归通过，保证每个生成的关卡确实可解。

## 日志 5：灾难恢复与签名重建（10/07–10/08）

开发中途整个工程目录被误删。恢复过程：

- 从保留的发布 APK 逆向恢复编译资源（字体/音频/图标）；
- 从开发环境的持久化记录中找回全部源码快照；
- 恢复后五个核心脚本编译产物与原 APK 逐字节一致（证明源码恢复无损）；
- 原签名密钥确实丢失 → 生成新 RSA-3072 发布密钥，versionCode 递增为 2（0.2.0 重签）→ 3（0.3.0）；密钥与密码存放工程目录之外。

最终态：v0.3.0 三平台包（Android APK v2 签名 + zipalign 通过、Windows、Linux），六个编译脚本与导出 pck 逐字节一致，全量测试 0 失败。这次事故的直接教训是密钥与源码的异地备份不能等发布后再做。
